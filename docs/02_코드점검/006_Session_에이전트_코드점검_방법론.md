# 에이전트 기반 코드 점검 방법론

> 작성일: 2026-02-22
> 프로젝트: "고양이를 지켜라" GPS 게임

## 배경

이 문서는 2026-02-22 세션에서 병렬 에이전트를 활용한 코드 점검을 설계한 경험을 기록합니다.
향후 에이전트 기반 작업 시 참고 자료로 활용합니다.

---

## 이번 세션에서 시도한 접근법

### 1차 시도: 단일 패스 점검
- 3개 Explore 에이전트를 병렬로 투입하여 프로젝트 전체를 탐색
  - Agent 1: 프로젝트 구조 + 아키텍처 파악
  - Agent 2: 변경된 12개 파일 상세 분석
  - Agent 3: 문서 + 계획 파일 분석
- 결과를 종합하여 19개 이슈를 도출하고 Sprint 1-4로 우선순위 분류
- **문제점**: 탐색과 분석이 한 번에 이루어져, 깊이가 부족하고 교차 검증이 없었음

### 2차 시도: 수정 중심 병렬 분할
- 파일 충돌 없도록 3개 영역으로 분할 (Android 핵심 / API 서버 / 게임 로직)
- 각 영역별 수정 에이전트 + 교차 평가 에이전트 + 통합 에이전트 (Wave 1-2-3)
- **문제점**: 분석 없이 바로 수정으로 넘어가는 구조 → 사용자가 점검 결과를 확인하기 전에 코드가 변경됨

### 3차 시도 (최종 채택): 분석 전용 다층 점검
- 수정 없이 분석 문서만 작성
- Wave 1: 3개 에이전트가 각자 영역 분석 → 6개 문서
- Wave 2: 3개 에이전트가 교차 평가 → 3개 문서
- Wave 3: 종합 보고서 1개
- 총 10개 문서를 `docs/agents/`에 생성
- 이후 종합 결과 기반으로 별도 수정 플랜 수립

## 무엇이 효과적이었나

### 병렬 Explore 에이전트의 초기 탐색
- 3개 에이전트를 동시에 돌려 프로젝트 전체 구조를 80초 내에 파악
- 각 에이전트에 **명확히 다른 초점**을 부여한 것이 핵심
  - 구조 탐색 vs 코드 분석 vs 문서 분석으로 겹침 최소화
- 결과: 프로젝트 기술 스택, 아키텍처, 게임 메커니즘, 현재 진행 상태 등 종합적 이해 확보

### Plan 에이전트의 설계 역할
- 탐색 결과를 바탕으로 19개 이슈를 체계적으로 정리
- 의존성 그래프와 실행 순서까지 도출
- 단순 나열이 아닌 **구조화된 분석**을 산출

## 무엇이 부족했나

### 1. 탐색 ↔ 분석 ↔ 수정의 단계 구분 부재
- 처음에 탐색과 수정 계획을 한 번에 하려 함
- **교훈**: 탐색 → 분석 문서화 → 사용자 검토 → 수정 계획 → 수정 실행으로 단계를 명확히 분리해야 함

### 2. 교차 평가 설계의 구체성 부족
- "다른 영역 관점에서 재평가"라는 지시가 추상적
- **교훈**: 교차 평가 에이전트에게 구체적 질문 목록을 제공해야 함
  - 예: "ApiService의 인증 헤더 형식이 game.ts의 미들웨어와 호환되는가?"
  - 예: "SyncManager의 충돌 해결이 GameRepository의 upsert와 정합성이 있는가?"

### 3. 에이전트 결과 품질 편차
- 일부 에이전트는 매우 상세한 라인 번호까지 포함한 반면, 다른 에이전트는 개략적
- **교훈**: 산출물 템플릿을 명시적으로 제공하여 품질 균일화

## 다음에 더 잘하려면

### 원칙 1: 단계 분리 (Separation of Phases)
```
Phase 1: Explore (탐색) — 코드 구조, 패턴, 기술 스택 파악
Phase 2: Analyze (분석) — 이슈 발견, 문서화, 심각도 분류
Phase 3: Cross-Review (교차 평가) — 다른 에이전트 결과 검증
Phase 4: Synthesize (종합) — 최종 보고서 + 수정 플랜
Phase 5: Execute (실행) — 실제 코드 수정 (별도 세션)
```

### 원칙 2: 에이전트 프롬프트 품질 관리
- 각 에이전트에게 제공할 것:
  1. **명확한 범위**: 점검할 파일 목록 + 절대 경로
  2. **구체적 질문**: "X가 Y와 호환되는가?" 형태
  3. **산출물 템플릿**: 마크다운 구조 + 필수 섹션
  4. **금지 사항**: "코드를 수정하지 마라", "추측하지 말고 코드를 읽어라"
  5. **컨텍스트**: 이전 Phase의 결과 요약

### 원칙 3: 파일 소유권 (File Ownership)
- 병렬 에이전트가 **같은 파일을 수정하면 충돌** 발생
- 파일을 에이전트에 배타적으로 할당
- 교차 의존 파일은 마지막 통합 단계에서만 수정

### 원칙 4: 평가 에이전트의 구체적 체크리스트
- 추상적 "검토해라" 대신 Yes/No 질문 목록 제공:
  - [ ] 함수 시그니처가 호출측과 일치하는가?
  - [ ] 에러 타입이 catch 블록과 매칭되는가?
  - [ ] 직렬화 형식이 서버/클라이언트 양쪽에서 동일한가?

### 원칙 5: 에이전트 수의 적정화
- 병렬 에이전트 최대 3개 (Tool 제한)
- 너무 세분화하면 컨텍스트 전달 오버헤드 증가
- **적정 분할**: 기능 영역 기준 (인프라 / 비즈니스 로직 / 외부 인터페이스)

## 에이전트 유형별 활용 가이드

| 에이전트 유형 | 적합한 작업 | 부적합한 작업 |
|-------------|-----------|-------------|
| Explore | 코드 탐색, 패턴 파악, 파일 찾기 | 코드 수정, 빌드 실행 |
| Plan | 이슈 분류, 수정 전략 설계, 의존성 분석 | 실제 구현, 테스트 실행 |
| Bash | 빌드, 테스트, git 작업 | 코드 분석 (느리고 비효율) |
| general-purpose | 복합 작업, 문서 작성 + 코드 수정 | 단순 파일 검색 |
