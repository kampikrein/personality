# 에이전트 구성 업그레이드 — 타로 모바일 확장

## 작업 목표

PRD(docs/003_gemini_deep_research.md)가 정의한 타로 모바일 앱 요구사항을 현재 에이전트 조직이
커버하지 못하는 영역을 식별하고, 연구 기반으로 에이전트 구성을 업그레이드한다.

**제약**:
- 기존 5개 에이전트의 검증된 구조(SOP, 기억 시스템, 협업 규칙)를 재활용
- docs/05_agent_design의 원칙 유지: "행동 규칙 > 역할 선언", 도메인 지식 외부 배치

**성공 기준**:
- PRD의 모든 기술 영역(Flutter, 물리엔진, 센서API, 소셜, 커스텀덱)에 담당 에이전트가 존재
- 사용자 관점 품질 평가 프로세스가 에이전트로 정의됨
- 커뮤니티 페인포인트가 에이전트 설계에 반영됨
- 기존 에이전트와의 협업 관계가 명확히 정의됨

## 접근 방향

**선택된 접근**: 연구 우선 (Research-First) → 설계 → 구현

1. 외부 연구를 통해 타로앱 사용자 불만, 멀티에이전트 구성 사례, Flutter 개발 패턴, UX 평가 방법론을 수집
2. 연구 결과를 기반으로 신규 에이전트 정의 + 기존 에이전트 조정 범위 결정
3. 에이전트 파일 작성, 오케스트레이션 프로토콜 업데이트, CLAUDE.md 반영

**대안 (미선택)**:
- 즉시 설계: 연구 없이 갭 분석만으로 에이전트 추가 → 커뮤니티 인사이트 누락 위험
- 점진적 추가: 에이전트를 하나씩 추가하며 테스트 → 전체 아키텍처 정합성 부족 위험

## Research 판단
- **판단**: 필요
- **근거**: 사용자가 명시적으로 웹/커뮤니티/사례 연구를 요청. 외부 API(Flutter), 미사용 프레임워크(모바일 물리엔진), 프로젝트 유사 패턴 없음
- **파이프라인**: S → R → P → I(V)

## 사이클별 연구 가이드

### 사이클 1: 외부 연구

**5대 조사 축**:

#### 1. 타로 앱 커뮤니티 페인포인트
- 조사 대상: Reddit (r/tarot, r/tarotpractice), App Store/Play Store 리뷰, 타로 커뮤니티 포럼
- 핵심 질문:
  - 기존 타로 앱에서 사용자들이 가장 불만족하는 점은?
  - "영적 연결감 부족"에 대한 구체적 불만 사례는?
  - 커스텀 덱/셔플에 대한 수요가 실제로 있는가?
  - 소셜/커뮤니티 기능에 대한 기대와 우려는?

#### 2. 멀티에이전트 시스템 구성 사례
- 조사 대상: AI agent team composition 연구, Claude Code agent 사례, multi-agent 프레임워크
- 핵심 질문:
  - 모바일 + 서버 혼합 프로젝트에서 에이전트를 어떻게 분리하는가?
  - 도메인 전문가 vs 기술 전문가 에이전트의 최적 비율은?
  - 에이전트 수가 늘어날 때 오케스트레이션 복잡도 관리 방법은?
  - 평가/QA 에이전트의 역할 정의 사례는?

#### 3. Flutter/모바일 개발 에이전트 패턴
- 조사 대상: Flutter 프로젝트의 AI 에이전트 활용 사례, 모바일 앱 개발 자동화
- 핵심 질문:
  - Flutter 전문 에이전트에 필요한 핵심 지식은?
  - 물리 엔진/애니메이션 전문성을 별도 에이전트로 분리해야 하는가?
  - 오프라인-퍼스트, 센서API 등 모바일 특수 영역의 에이전트 커버리지는?

#### 4. UX 평가/QA 에이전트 방법론
- 조사 대상: UX 평가 자동화 도구, 히유리스틱 평가 체크리스트, 사용성 테스트 방법론
- 핵심 질문:
  - 사용자 관점 평가 에이전트의 역할 범위는? (UX 감사, 접근성, 성능, 감정 흐름)
  - 평가 에이전트와 구현 에이전트의 피드백 루프 설계는?
  - 자동화 가능한 평가 항목 vs 수동 검증이 필요한 항목은?

#### 5. 타로 도메인 에이전트 필요성 검증
- 조사 대상: 타로 앱 시장 분석, 타로 리딩 프로세스 구조화
- 핵심 질문:
  - 타로 도메인 지식을 별도 에이전트로 분리해야 하는가, 아니면 참조 문서로 충분한가?
  - MBTI/애니어그램 에이전트와 타로 에이전트의 관계는? (보완? 독립?)
  - 타로 에이전트가 커버해야 할 도메인 범위는? (전통 해석, 현대 해석, 셔플 의식 등)

## 체크포인트 & 컨텍스트 관리

### 파이프라인 체크포인트

| 체크포인트 | 산출물 | 컨텍스트 조치 | 판단 기준 |
|-----------|--------|-------------|----------|
| /scope 완료 | 이 문서 | /clear 권장 | 다음이 /research (독립적 넓은 탐색) |
| /research 완료 | Research 문서 | /clear | research는 광범위 외부 탐색, 다음 makeplan에 노이즈 |
| /makeplan 완료 | Plan 문서 | 유지 또는 /compact | plan에서 읽은 에이전트 파일 = impl에서 수정할 파일 |
| /implementation 완료 | 에이전트 파일 + 프로토콜 | 완료 | — |

### /clear 후 복원 방법
- Scope 문서 → 작업 목표, 갭 분석, 연구 가이드
- Research 문서 → 외부 조사 결과, 커뮤니티 인사이트
- Plan 문서 → 에이전트 정의 상세, 구현 체크리스트
