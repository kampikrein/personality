# 커뮤니티 AI 답변 + 콘텐츠 출처 신뢰도 시스템

## Intent

personality 타로 앱의 **커뮤니티(소통) 탭**에 **P2P 타로 해석 기능**을 구현한다.

**핵심 경험**: 유저가 자신의 리딩(뽑힌 카드 + 질문)을 커뮤니티에 공유하면, 다른 유저가 해석을 달아줄 수 있다. 이때 AI를 보조 도구로 활용하여 답변을 생성하거나 보강할 수 있으며, 시스템이 각 답변의 **작성 방식**(AI 생성 / 직접 타이핑 / 복사붙여넣기)을 감지하여 **간접 신뢰도 지표**로 표시한다.

**차별점**: 기존 AI 타로 해석 서비스는 "AI → 유저" 단방향이지만, 이 기능은 "유저 ↔ 유저" 관계에 AI를 보조 도구로 끼워 넣는 **소셜 해석** 모델이다. 콘텐츠 출처 감지를 통해 AI 활용을 숨기지 않고 투명하게 만들면서도, 직접 작성한 답변에 더 높은 신뢰 가치를 부여한다.

## Context

### 현재 코드베이스 상태

- **Community feature**: `mobile/lib/features/community/` — 플레이스홀더만 존재 (`CommunityPage` "곧 추가됩니다")
- **Chat feature**: `mobile/lib/features/chat/` — AI 채팅 플레이스홀더 (별도 주제 `docs/12_ai_tarot_chat/`)
- **Reading 도메인**: `Reading` 엔티티(deckId, spreadType, question, drawnCards) — 커뮤니티 공유의 입력 데이터
- **Card 데이터**: `TarotCard`, `CardMeanings` — 답변 작성 시 AI가 참조할 카드 의미 데이터
- **Server**: Rails 8+ 백엔드 (PostgreSQL, 아직 커뮤니티 API 미구현)
- **기존 연구**: `docs/12_ai_tarot_chat/` — AI 해석 사전 연구 완료 (LLM API, 프롬프트, 개인화 파이프라인), 이 연구의 AI 기술 스택 결정이 커뮤니티 AI 답변에도 재활용 가능

### 관련 기존 연구

- `docs/11_global_tarot_market/` — "AI + 맥락 지속성"이 차별화 요인, 커뮤니티형 서비스는 소수
- `docs/12_ai_tarot_chat/` — AI 해석 기술 조사 완료, LLM API 비교, 프롬프트 설계 방향
- `server/app/services/quality/bot_detector.rb` — 기존 봇 감지 서비스 존재 (성격 검사용, 재활용 가능성)
- `server/app/services/quality/speed_analyzer.rb` — 응답 속도 분석 서비스 존재 (입력 패턴 분석에 활용 가능)

## Boundaries

### In Scope
| # | Item | Description |
|---|------|-------------|
| 1 | 리딩 공유 구조 | 유저가 자신의 리딩(카드+질문)을 커뮤니티에 게시하는 데이터 모델 및 흐름 |
| 2 | P2P 해석 답변 | 다른 유저가 공유된 리딩에 해석 답변을 다는 기능 구조 |
| 3 | AI 보조 답변 생성 | 답변 작성 시 AI를 도구로 활용하여 초안 생성/보강하는 메커니즘 |
| 4 | 콘텐츠 출처 감지 | 답변의 작성 방식(AI 생성/타이핑/복붙)을 분류하는 알고리즘 설계 방향 |
| 5 | 간접 신뢰도 표시 | 출처 감지 결과를 UX에 반영하는 신뢰도 지표 시스템 |
| 6 | 기존 서비스 참조 | bot_detector, speed_analyzer 등 기존 품질 서비스와의 연결 가능성 |

### Out of Scope
| # | Item | Reason |
|---|------|--------|
| 1 | 실시간 채팅/DM | 커뮤니티 답변은 비동기 게시판형, 실시간 채팅은 별도 주제 |
| 2 | AI 자동 답변 (봇 계정) | AI는 유저의 도구이지, 독립적 답변자가 아님 |
| 3 | 유저 평판/레벨 시스템 | 간접 신뢰도는 콘텐츠 단위, 유저 전체 평판은 후속 |
| 4 | 모더레이션/신고 시스템 | 커뮤니티 관리 기능은 별도 scope |
| 5 | Flutter UI 구현 | 본 Brief는 설계 방향까지, 구현은 후속 파이프라인 |
| 6 | Rails API 구현 | 서버 구현은 설계 완료 후 별도 진행 |

## Decisions

| # | Decision | Chosen | Rationale | Trade-off | Alternatives Considered |
|---|----------|--------|-----------|-----------|------------------------|
| 1 | 커뮤니티 구조 | **Q&A형 (리딩 공유 → 해석 답변)** | 사용자 요청이 "다른 사람의 카드에 답변"을 명시 — 이는 질문-답변 구조를 자연스럽게 함의. 타로 리딩 자체가 "질문 → 카드 뽑기 → 해석"의 구조이므로, 리딩을 게시하고 해석을 받는 Q&A 패턴이 도메인에 가장 적합. 피드형은 탐색에 유리하나 해석의 구조화가 약하고, 포럼형은 대화가 발산되어 해석 품질이 희석됨 | 피드형 대비 발견성(discoverability)이 떨어짐 — 인기/최신/태그 필터링으로 보완 | 피드형 (인스타/타임라인) — 해석보다 공유에 초점이 맞춰져 사용자 요청의 핵심(답변)에서 벗어남; 포럼형 (스레드) — 대화가 해석에서 벗어나 발산될 위험, 도메인 특성상 구조화된 해석이 더 가치 있음 |
| 2 | AI 역할 모델 | **유저의 답변 작성 보조 도구 (AI-assisted draft)** | "다른 사람이 AI로 답변할 수 있도록" — AI가 독립적 답변자가 아니라 유저의 도구. 유저가 AI 초안을 생성하고, 수정/보강하여 게시하는 모델. 이유: (1) 답변의 주체가 유저여야 커뮤니티 가치가 생김, (2) AI 직접 답변이면 모든 리딩에 균일한 AI 답변이 달려 차별화 없음, (3) `docs/12_ai_tarot_chat/`의 AI 직접 해석과 역할이 겹침 | 순수 수동 작성 대비 진입 장벽이 낮아지나, AI에 과도하게 의존하면 답변 균질화 위험 — 출처 감지 + 신뢰도 차등으로 자연 조절 | AI 독립 답변 (봇 계정) — 커뮤니티의 인간적 가치 훼손, `12_ai_tarot_chat`과 중복; AI 없이 순수 수동만 — 타로 해석 지식 장벽이 높아 답변 수 극감, 커뮤니티 활성화 실패 위험 |
| 3 | 콘텐츠 출처 감지 접근 | **하이브리드 (클라이언트 메타데이터 + 서버 분류)** | 3가지 감지 대상: (A) AI 생성 — 앱 내 AI 버튼 사용 시 클라이언트가 플래그 전송 (100% 정확), (B) 복사붙여넣기 — 클라이언트가 클립보드 paste 이벤트 감지 + 서버에서 타이핑 시간 대비 텍스트 양 비율 분석, (C) 직접 타이핑 — A, B가 아닌 경우 기본값. 서버의 기존 `speed_analyzer.rb` 패턴을 재활용하여 키스트로크 시간 분석 가능. 순수 서버사이드 AI 텍스트 감지(GPTZero류)는 정확도 불안정 + 외부 API 의존이므로 보조적 역할만 | 클라이언트 메타데이터 조작 가능성 — 그러나 "간접 신뢰도"이므로 100% 정확도가 목표가 아님. 조작 인센티브도 낮음 (신뢰도가 점수/랭킹이 아니라 라벨이므로) | 순수 서버사이드 AI 감지 — GPTZero류 API 정확도 70~85%로 불안정, 비용 발생, false positive 시 유저 경험 훼손; 자기 신고제 — 정직성에 의존하여 신뢰도 시스템의 의미 상실; 순수 클라이언트만 — 서버 검증 없이는 조작 취약 |
| 4 | 신뢰도 표시 방식 | **투명 라벨형 (작성 방식 표시)** | "AI로 생성한건지 타자를 친건지 복붙한건지 체크해주는" — 점수가 아닌 작성 방식 자체를 표시하는 것이 사용자 요청에 가장 부합. 예: `✍️ 직접 작성`, `🤖 AI 보조`, `📋 붙여넣기 포함`. 점수형(0~100)은 과도하게 판단적이고 타로 커뮤니티의 수용적 분위기와 충돌. 라벨은 정보 제공이지 등급 매기기가 아님 | 숫자 점수 대비 정밀한 비교 불가 — 그러나 타로 해석의 가치는 정량화 불가, 라벨이 더 적절 | 점수형 (0~100 신뢰도) — 해석의 질을 수치화하는 것은 타로 도메인의 주관적 특성과 충돌, 유저 간 경쟁/비교 유발; 배지형 (인증 마크) — "인증된 해석"이라는 개념 자체가 타로의 다양성을 부정, 권위 부여는 위험 |
| 5 | 기존 12_ai_tarot_chat과의 관계 | **독립 주제, AI 기술 스택만 공유** | `12_ai_tarot_chat`은 "AI → 유저" 1:1 해석, 본 주제는 "유저 → 유저 (AI 보조)" P2P 해석 — 사용자 경험과 데이터 흐름이 근본적으로 다름. 그러나 AI 답변 생성에 사용하는 LLM API, 프롬프트 기반, 카드 의미 참조 로직은 공유 가능. 기술 인프라만 재활용하고 기능·UI·데이터 모델은 독립 설계 | 두 기능 간 기술 중복이 일부 발생 — 공통 서비스 계층(예: AI 해석 서비스)으로 추출하여 해결 | 12번에 통합 — P2P와 1:1의 UX가 근본적으로 달라 무리한 통합은 양쪽 모두 복잡도만 증가; 완전 독립 (기술도 분리) — 동일 LLM 연동 로직 이중 구현은 비효율 |
| 6 | 복합 출처 처리 | **혼합 라벨 허용 (가장 높은 비중 + 보조 라벨)** | 현실적으로 유저는 AI 초안을 받아 수정하거나, 일부 타이핑 + 일부 붙여넣기를 할 수 있음. 단일 라벨 강제는 부정확. 예: "🤖 AI 보조 + ✍️ 수정됨" (AI 초안을 유저가 40% 이상 수정), "✍️ 직접 작성 + 📋 일부 붙여넣기". 주 라벨 + 보조 라벨 구조로 작성 과정의 실체를 투명하게 반영 | 라벨이 복잡해지면 유저 혼란 — 주 라벨 1개만 크게 표시하고 보조는 탭 시 상세 노출로 해결 | 단일 라벨만 — 혼합 작성 시 부정확, 신뢰 훼손; 비율 표시 (AI 60%, 타이핑 40%) — 과도한 정밀도, UX 부담 |

## Constraints

- **기존 연구 활용**: `docs/12_ai_tarot_chat/` AI 기술 조사 결과를 AI 보조 답변 설계에 재활용
- **기존 서비스 활용**: `bot_detector.rb`, `speed_analyzer.rb` 패턴을 콘텐츠 출처 감지에 참조
- **전문 에이전트 위임**: 타로 해석 품질 → tarot-expert, 심리적 신뢰 메커니즘 → psychology-expert, 커뮤니티 UX → uiux-expert
- **문서 언어**: 한국어
- **코드 수정 없음**: 본 Brief는 설계 방향까지, 구현은 후속 파이프라인
- **도메인 감수성**: 타로 해석의 주관성을 존중 — 신뢰도 시스템이 "정답/오답"을 판단해선 안 됨
- **프라이버시**: 타이핑 패턴 수집 시 사용자 동의 + 최소 수집 원칙 준수

## Exit Criteria

1. 커뮤니티 리딩 공유 → 해석 답변의 데이터 흐름이 정의되어 있을 것
2. AI 보조 답변 생성의 유저 인터랙션 모델이 명확할 것
3. 콘텐츠 출처 감지(AI/타이핑/복붙)의 기술적 접근이 정의되어 있을 것
4. 간접 신뢰도 표시의 UX 방향이 결정되어 있을 것
5. 기존 코드(`Reading`, `bot_detector`, `speed_analyzer`)와의 연결 지점이 식별되어 있을 것
6. `12_ai_tarot_chat`과의 기술 공유 범위가 명확할 것

## Model Anchors

- **기능 유형**: P2P 커뮤니티 타로 해석 + 콘텐츠 출처 감지. AI 직접 해석(`12_ai_tarot_chat`)과 별개.
- **커뮤니티 구조**: Q&A형. 리딩(카드+질문) 게시 → 해석 답변. 실시간 채팅 아님, 비동기 게시판.
- **AI 역할**: 유저의 답변 작성 보조 도구. AI가 독립적 답변자가 아님. 유저가 AI 초안 생성 → 수정/보강 → 게시.
- **출처 감지 3분류**: (A) AI 생성 — 앱 내 AI 버튼 클릭 시 클라이언트 플래그, (B) 복붙 — paste 이벤트 + 타이핑 시간/텍스트 양 비율, (C) 직접 타이핑 — A, B 아닌 기본값. GPTZero류 외부 API는 보조적 역할만.
- **신뢰도 표시**: 투명 라벨형 (`✍️ 직접 작성`, `🤖 AI 보조`, `📋 붙여넣기 포함`). 점수/등급 아님. 혼합 시 주 라벨 + 보조 라벨.
- **기존 서비스 재활용**: `speed_analyzer.rb` → 타이핑 패턴 분석, `bot_detector.rb` → 이상 패턴 감지.
- **기술 공유**: `12_ai_tarot_chat`과 LLM API 연동 + 카드 의미 참조 로직 공유. UI/데이터 모델은 독립.
- **도메인 원칙**: 신뢰도는 "작성 방식의 투명성"이지 "해석 품질의 판단"이 아님. 타로 해석에 정답/오답 없음.
- **산출물 위치**: `docs/13_community_ai_reply/` 하위.
- **에이전트 위임**: 타로 해석 품질 기준 → tarot-expert, 신뢰/투명성 심리 → psychology-expert, 커뮤니티 UX → uiux-expert.
