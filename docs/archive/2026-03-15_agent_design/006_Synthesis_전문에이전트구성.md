## Cross-Analysis

### 공통 발견사항

1. **"행동 규칙 > 역할 선언" 원칙의 일관된 지지**
   - 관점 2(페르소나)에서 PromptHub 연구를 통해 확인: 단순 역할 선언은 성능에 기여하지 않음
   - 관점 1(시스템)에서도 도구/모델 선택보다 프롬프트 품질이 핵심이라고 결론
   - 관점 4(프로젝트)에서 구체적 산출물 명시가 에이전트 효용의 핵심이라고 강조

2. **자문 에이전트의 쓰기 권한 필요성**
   - 관점 1: 문항 텍스트, 점수 가중치, 보고서 문구 등 구체적 산출물 반영에 Write/Edit 필요
   - 관점 4: 미구현 영역이 "콘텐츠 레이어"(문항, 유형 해석, 인사이트)이므로 자문 에이전트가 직접 작성해야 효과적
   - 결론: 자문 에이전트도 Read+Write+Edit+Glob+Grep (Bash 제외) 조합이 적합

3. **도메인 지식은 프롬프트 외부에 배치**
   - 관점 2: 안티패턴 3번 — "도메인 지식 과다 주입"은 컨텍스트 소모
   - 관점 3: 에이전트당 수백 줄의 도메인 지식이 필요 → 프롬프트에 직접 넣으면 과부하
   - 결론: 프롬프트에는 "어떻게 사고하는가(HOW)"만 포함, 상세 지식은 참조 파일로 분리

4. **법적 경계 원칙은 모든 에이전트의 공통 레드라인**
   - 관점 2: 모든 에이전트의 Boundaries/Red Lines에 법적 경계 포함
   - 관점 3: MBTI(상표+저작권), 애니어그램(특정 검사지)의 법적 위험을 각각 상세 정리
   - 관점 4: 저작권 조사 결론을 에이전트 프롬프트 컨텍스트에 포함해야 함

### 상충 의견

1. **skills 연동 범위**
   - 관점 1: 최소화 권장 — ui-ux-pro-max만 예외
   - 관점 2: 도메인 지식 파일을 skills로 구성하는 방안 언급
   - 판단: 관점 1의 최소화 원칙이 적합. 도메인 지식은 skills가 아닌 docs/ 참조로 충분

2. **에이전트 간 직접 통신 필요성**
   - 관점 4: 순차 워크플로우/병렬 리뷰 시나리오에서 에이전트 간 협업 필요
   - 관점 1: 서브에이전트는 다른 서브에이전트를 호출할 수 없는 시스템 제약
   - 판단: 에이전트 간 협업은 부모 세션(사용자)이 중재. 각 에이전트의 산출물을 docs/에 저장하면 다음 에이전트가 참조 가능

### 시너지 효과

1. **5축 차별화 매트릭스** (관점 3 + 관점 4 결합)
   - 동일 기능에 대해 5개 에이전트가 각각 다른 축에서 판단:
     - 심리학: 학술적 근거 → "이것이 타당한가?"
     - MBTI: 문화적 적합성 → "한국 사용자가 공감하는가?"
     - 애니어그램: 성장 가능성 → "사용자의 성장을 돕는가?"
     - 코딩: 구현 가능성 → "Rails 컨벤션으로 구현 가능한가?"
     - UI/UX: 사용자 경험 → "감정 흐름에 적합한가?"

2. **콘텐츠 갭 = 자문 에이전트의 핵심 기여** (관점 4 + 관점 3 결합)
   - 기술 인프라(14모델, 19서비스)는 대부분 구현됨
   - 부족한 것은 "학술 근거 있는 문항", "독자적 유형 해석", "인사이트 콘텐츠"
   - 자문 에이전트 3인(심리학, MBTI, 애니어그램)이 바로 이 갭을 채우는 역할

3. **프롬프트 구조 + 시스템 설정의 결합** (관점 2 + 관점 1 결합)
   - 관점 2의 7섹션 프롬프트 구조(Role → Project Context → Core Principles → Analysis Framework → Communication Style → Boundaries → Collaboration)
   - 관점 1의 시스템 설정(tools, model=sonnet, permissionMode=acceptEdits, maxTurns)
   - 이 두 가지를 `.claude/agents/*.md` frontmatter + body로 정확히 매핑 가능

## Comprehensive Conclusion

### 핵심 발견 (우선순위 순)

1. **[Critical] 프롬프트 설계 원칙**: 단순 역할 선언이 아닌 **구체적 행동 규칙 + 판단 프레임워크 + 레드라인**의 3요소가 에이전트 성능의 핵심. (관점 2, 1)

2. **[Critical] 콘텐츠 갭이 최대 병목**: 기술 인프라는 구현되어 있으나 학술적 근거 있는 문항·유형 해석·인사이트가 부족. 자문 에이전트 3인의 즉시 기여 가능 영역. (관점 4, 3)

3. **[High] 자문 에이전트도 쓰기 권한 필요**: 문항 텍스트, 점수 체계, 보고서 문구를 직접 코드에 반영해야 하므로 Read/Write/Edit/Glob/Grep (Bash 제외) 필요. (관점 1, 4)

4. **[High] 도메인 지식은 프롬프트 외부 배치**: 프롬프트에는 사고 방식(HOW)만 포함하고, 도메인 지식(WHAT)은 docs/ 참조 파일로 분리해야 컨텍스트 효율성 확보. (관점 2, 3)

5. **[High] 5축 차별화 구조**: 동일 기능에 대해 학술근거/문화적합/성장가능/구현실용/사용자경험이라는 5개 축에서 각각 다른 판단을 내리는 구조가 멀티에이전트의 핵심 가치. (관점 3, 4)

6. **[Medium] 법적 경계 원칙 공통 내장**: 모든 에이전트의 프롬프트에 법적 경계(MBTI 상표, 공식 문항 미사용 등)를 레드라인으로 포함. CLAUDE.md에 공통 규칙 배치도 고려. (관점 2, 3, 4)

7. **[Medium] 모든 에이전트 sonnet 모델**: haiku는 부족, opus는 과다. 서브에이전트 특성상 sonnet의 비용-성능 밸런스가 최적. (관점 1)

8. **[Medium] 에이전트 간 협업은 부모 세션 중재**: 시스템 제약상 서브에이전트 간 직접 통신 불가. docs/ 문서를 통한 비동기 협업이 현실적. (관점 1, 4)

### Recommended Actions

1. 5개 에이전트 `.claude/agents/*.md` 파일 생성 (관점 2 초안 + 관점 1 설정 결합)
2. 도메인 지식 참조 파일을 docs/ 또는 별도 위치에 구성 (관점 3 기반)
3. 코딩/UI/UX 에이전트 먼저 테스트 → 자문 에이전트 추가 (관점 1 단계적 도입)
4. 콘텐츠 갭 해소를 위해 자문 에이전트의 첫 작업은 "기존 문항/유형 설명 검토 및 개선" (관점 4)
